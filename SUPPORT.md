# Support

OPSd is designed to be usable self-serve first. Support exists to shorten the
time to a safe first result, not to replace ownership of the generated output.

## When To Use Support

Use support for:

- choosing a supported path
- reviewing the first manifest or workflow
- getting help with the first deployment
- adapting the workflow to a real team or rollout

## What Support Is Not For

Support is not the right channel for:

- undocumented provider combinations
- hand-editing generated infrastructure code
- custom behavior outside the supported blueprint and variant boundary
- ongoing managed operations unless that is explicitly agreed elsewhere

## How To Reach Us

Use the public support contact at `support@opsd.io`.

If you just want general product contact, use `hello@opsd.io`.

The public support and supported-paths model is described on the OPSd website.

## What To Include

Include the following in a support request when possible:

- OPSd version
- operating system and shell
- command you ran
- expected result
- actual result
- manifest or blueprint name if relevant
- relevant logs or output

If the request concerns a workspace, include the provider and whether the
workspace uses local blueprints or a cached provider release.
